# Big Data Interview Questions — 40+ with Answers

## Fundamentals

**Q1. What are the 3 V's of Big Data (and the 2 later additions)?**
> Volume, Velocity, Variety — later expanded with Veracity (quality/trust) and Value (worth processing).

**Q2. Why can't a single powerful machine handle "big data" workloads?**
> Even the most powerful single machines have hard ceilings on CPU/RAM/storage that petabyte-scale datasets and millions-of-events-per-minute velocities exceed — requiring horizontal distribution across many machines instead.

**Q3. What's the difference between scale-up and scale-out?**
> Scale-up = bigger single machine (simple, hard ceiling, single point of failure); scale-out = more machines working together (theoretically unlimited, but requires solving partitioning/fault-tolerance/coordination problems).

## Hadoop

**Q4. Explain how HDFS achieves fault tolerance.**
> Files are split into blocks, each replicated (default 3x) across different machines/racks — losing one or even two copies of a block still leaves it recoverable from a surviving replica.

**Q5. What's the role of the NameNode vs DataNodes?**
> NameNode stores metadata (which blocks make up which file, and where each replica lives) — doesn't store actual data; DataNodes store and serve the actual block data.

**Q6. Why was MapReduce slow compared to Spark for multi-step pipelines?**
> MapReduce writes intermediate results to DISK between every phase (map, shuffle, reduce); Spark keeps intermediate data in memory across stages whenever possible, avoiding repeated disk I/O.

**Q7. What is the Hive Metastore and why does it remain relevant today?**
> A persistent catalog of table schema/location/partition metadata originally built for Hive — its format became a de facto standard that modern tools (AWS Glue Data Catalog, Databricks Unity Catalog) remain compatible with.

## Spark

**Q8. Explain the Driver vs Executor relationship.**
> The Driver runs your main code, builds the execution plan, and coordinates work but doesn't process data at scale itself; Executors are JVM processes on worker nodes that actually run tasks and hold cached data. Pulling too much data to the Driver (via `.collect()`) can cause an OOM crash.

**Q9. What's the difference between a narrow and a wide transformation?**
> Narrow (filter, map, select): each output partition depends on only one input partition, no data movement needed. Wide (groupBy, join, distinct): output depends on multiple input partitions possibly on different machines, requiring an expensive shuffle and creating a new stage boundary.

**Q10. Why is Spark's DataFrame API generally faster than raw RDD code for the same logical operation?**
> The Catalyst optimizer can analyze and optimize declarative DataFrame operations (predicate pushdown, column pruning) — it can't see into and optimize opaque user-defined RDD lambda functions the same way. Tungsten also provides off-heap memory management and generated bytecode for DataFrame operations.

**Q11. What is lazy evaluation and why does Spark use it?**
> Transformations build a plan but don't execute until an action is called — this lets Spark see the ENTIRE chain of operations and optimize it globally, rather than executing and optimizing each step in isolation.

**Q12. How would you diagnose a slow Spark job?**
> Start with the Spark UI — check for data skew (one task dramatically slower than peers in the same stage), unnecessary/excessive shuffles, and memory pressure signals, before guessing at a fix.

**Q13. What is data skew and how do you fix it?**
> One partition/key holds disproportionately more data than others, creating a bottleneck task. Fixes: salting the key to spread it across more partitions, broadcast joins for small-table joins, or enabling Adaptive Query Execution (Spark 3.0+) to handle it automatically.

**Q14. Why avoid Python UDFs when a native Spark function exists?**
> Python UDFs require serializing data between the JVM and a separate Python process for every row, adding significant overhead; native Spark functions execute entirely within the JVM's optimized Tungsten engine.

**Q15. When should you cache a DataFrame, and when should you NOT?**
> Cache when it will genuinely be reused multiple times downstream; don't cache a DataFrame used only once — caching adds memory pressure and materialization overhead for zero reuse benefit.

## Streaming

**Q16. Why doesn't Kafka guarantee ordering across an entire topic?**
> Ordering is only guaranteed WITHIN a single partition; a topic with multiple partitions has no cross-partition ordering guarantee — which is why keying by a meaningful field (e.g., customer_id) matters for per-entity ordering.

**Q17. What's a Kafka consumer group and why does it matter?**
> Multiple consumer instances sharing the work of reading a topic — Kafka automatically assigns different partitions to different consumers within the same group, enabling parallel, load-balanced processing.

**Q18. Explain watermarking in streaming aggregations.**
> A threshold defining how late an event can arrive and still be counted in its time window — necessary because streaming systems can't wait forever for possibly-late data before finalizing and emitting window results.

**Q19. How do you practically achieve "exactly-once" processing?**
> At-least-once delivery (Kafka's default durability model) combined with IDEMPOTENT processing logic (MERGE/UPSERT keyed on a unique ID) — the pragmatic standard approach, since true end-to-end exactly-once infrastructure guarantees are genuinely hard to achieve.

**Q20. Spark Structured Streaming vs Flink — how do you choose?**
> Spark Structured Streaming (micro-batch) is preferred when a team already uses Spark for batch (unified skills/codebase) and "seconds" latency is acceptable; Flink (true event-at-a-time) is chosen when sub-second/millisecond latency is a hard business requirement.

## Lakehouse Formats

**Q21. Why can't you just UPDATE a row in a plain Parquet file?**
> Parquet files are immutable by design; modifying one row would require rewriting the entire file. Lakehouse formats (Delta/Iceberg/Hudi) add a transaction log tracking file-level changes, enabling efficient row-level updates/deletes.

**Q22. Why did Netflix create Iceberg instead of using existing Hive tables?**
> Hive's partition-directory-based metadata tracking became a bottleneck at Netflix's file-count scale; Iceberg tracks individual files in its metadata layer, enabling more efficient query planning and safer concurrent writes at massive scale.

**Q23. Why did Uber create Hudi specifically?**
> Uber's trip records are updated frequently as a ride progresses through status changes — Hudi's indexing-based storage layout makes frequent point-updates dramatically more efficient than naive full-partition rewrites.

**Q24. What's "time travel" and why does it matter in production?**
> Querying a table as it existed at a previous point in time — useful for debugging (comparing against a known-good historical state), regulatory/compliance reconstruction, and safe rollback without a separate backup system.

## Cloud & Distributed Computing

**Q25. Why has Kubernetes overtaken YARN as the dominant cluster manager for new deployments?**
> Kubernetes isn't big-data-specific — the same cluster running Spark jobs can also run web services, databases, and ML training, letting companies standardize infrastructure operations around ONE platform instead of maintaining a separate YARN cluster just for big data.

**Q26. How does Spark achieve fault tolerance without HDFS-style full replication of every intermediate result?**
> RDD lineage — Spark tracks the chain of transformations that produced each partition and can recompute a lost partition from its lineage rather than needing a stored replica, appropriate for transient computation vs HDFS's persistent storage use case.

**Q27. Databricks vs EMR — what's the real tradeoff?**
> Databricks offers a more abstracted, managed platform with an optimized Spark runtime, Delta Lake nativity, and unified data+ML tooling (faster time-to-value, some vendor lock-in); EMR offers lower-level infrastructure control (more operational responsibility, typically lower direct cost, more flexibility).

## Real-World / Company Choices

**Q28. Why did LinkedIn create Kafka instead of using an existing message queue?**
> Existing message queues didn't handle LinkedIn's need for high-throughput, durable, REPLAYABLE event logs that multiple independent internal systems could consume at their own pace — a genuinely new requirement pattern.

**Q29. Why did Airbnb create Airflow?**
> As their number of interdependent scheduled data pipelines grew into the hundreds, manually tracking dependencies/schedules/failures became unmanageable, directly motivating a dedicated orchestration tool.

**Q30. What's the recurring pattern behind most major big data tools (Kafka, Airflow, Iceberg, Hudi, Presto)?**
> Nearly all were built INTERNALLY at a specific company to solve their own specific scaling pain point, then open-sourced and adopted broadly — recognizing a genuine tooling gap and building the right solution is itself a senior data engineering skill.

## Rapid-Fire
31. What's a shuffle in Spark and why is it expensive? *(Moving data across the network between executors for wide transformations like groupBy/join — expensive due to network + disk I/O.)*
32. What's the difference between `coalesce()` and `repartition()`? *(Coalesce reduces partitions without a full shuffle; repartition can increase or decrease but always triggers a full shuffle.)*
33. What's a broadcast join? *(Copying a small table in full to every executor to avoid shuffling a huge table it's being joined against.)*
34. What's the small-files problem? *(Many tiny files cause excessive file-open/close overhead relative to actual data processing time; fixed via periodic compaction.)*
35. What's Adaptive Query Execution (AQE)? *(Spark 3.0+ feature that adjusts the execution plan at RUNTIME based on actual data statistics, including automatic skew handling.)*
36. What's the difference between at-least-once and exactly-once processing? *(At-least-once may process duplicates on retry; exactly-once guarantees single processing, typically achieved practically via at-least-once + idempotent logic.)*
37. What's a tumbling window vs a sliding window? *(Tumbling: fixed, non-overlapping; sliding: fixed size but overlapping, advancing by a smaller step.)*
38. Why explicitly define a schema instead of using `inferSchema=True`? *(Avoids an extra data pass just to guess types, and avoids incorrect type inference on edge-case data.)*
39. What's the purpose of Zookeeper in distributed systems like Kafka/HBase? *(Distributed coordination — leader election, configuration management, cluster membership.)*
40. Why is Presto/Trino often preferred over Hive for ad-hoc analyst queries? *(In-memory, no MapReduce-style overhead — optimized for fast INTERACTIVE query response, unlike Hive's traditionally batch-oriented execution.)*
